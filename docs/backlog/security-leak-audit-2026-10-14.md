## 1. Что требует действия

### Medium

**A1. Карточка участника отдаёт профиль любого пользователя платформы** ✅ исправлено 2026-10-14 (эта ветка; заодно рядовому участнику карточка только активного — зеркало ростера)
`backend/src/main/kotlin/com/clubs/membership/MemberService.kt:87-95` — `GET /api/clubs/{clubId}/members/{userId}`
проверяет, что **вызывающий** — активный участник `clubId`, но не проверяет, что **`userId`** имеет
отношение к этому клубу. `userRepository.findById(userId)` находит кого угодно.
- Утекает: имя, `@username`, аватар, bio, интересы человека, с которым вызывающий не состоит ни в
  одном клубе. Организаторские поля и Trust не утекают (они по членству в этом клубе → null).
- Сценарий: создать свой клуб (сразу активный организатор) → взять чужой UUID (`ownerId` любого
  клуба из каталога, `userId` из долгов/откликов) → `GET /api/clubs/<свой>/members/<чужой>` → 200.
- Правка: требовать строку членства `userId` в `clubId` (любой статус — менеджеру нужны и
  frozen/expired), иначе 404. Один файл + тест в `MemberServiceVisibilityTest`.

**A2. «Кто берёт?» после заказа: в групповой пост попадают @-упоминания неоплативших** ℹ️ PO 2026-10-14: оставить (исключение записано в `skladchina-v3.md` § 6)
`backend/src/main/kotlin/com/clubs/chatlink/SkladchinaChatStatusRenderer.kt:140-146` — после «Заказываю»
пост в чате: «⏳ Ждём оплату: 2 · @Иван, @Пётр» и висит до оплаты. Для обычных сборов после срока
имена в чат не идут (решение PO 2026-09-12, `sharedText` реализован верно), в спеке § 6 для
«`per_head`, заказано» имён нет. В группе могут быть не-участники клуба; публичная супергруппа видна всем.
- Варианты: (а) оставить только число, меншены убрать — одна строка; (б) PO считает это осознанным
  («купил в долг — пусть видно, кого ждём») → дописать исключение в спеку.

**A3. Скриншоты оплаты и чеки — публичные URL без входа, навсегда, с EXIF** ⏸ PO 2026-10-14: оставить как есть
`frontend/nginx.conf:65-79` (`/uploads/` → MinIO без JWT, `Cache-Control: public, max-age=1y`),
`backend/.../storage/StorageService.kt:75` (bucket-policy `public-read`), `StorageController.kt:56-58`.
- Что лежит: `duesProofUrl` (скриншот перевода взноса — ФИО, банк, телефон, сумма), `receiptUrl`
  (чек по долгу), фото встреч/сборов, аватары. На уровне API ссылки гейтятся верно, но сам объект
  открывается любому, у кого есть ссылка. Защита — только непредсказуемость UUID v4 (перебор
  нереален, листинг бакета невозможен — проверено).
- EXIF: `frontend/src/utils/imageUpload.ts:78` — файлы ≤ 200 КБ, влезающие в размер, и все чеки
  (намеренно не сжимаются) уходят оригиналом с GPS/датой; бэк тоже не чистит. Фото встречи с
  GPS-тегом бот постит в чат.
- Правка: для `duesProof`/`receipt` — отдача через бэк с JWT (или подписанные URL) и
  `Cache-Control: private`; strip EXIF на бэке для всех картинок; проверять magic bytes, а не
  `file.contentType` со слов клиента (`StorageController.kt:41-46`). Это отдельная задача
  (storage + nginx + миграция политики бакета), не точечная правка.

## 2. By design — правки не нужно, но стоит знать

- **Адрес, гео-кнопка, фото и причина отмены встречи публикуются в группу** (`EventMessageTemplate.kt:50`,
  `LivePinRenderer.kt:59-129`, `LivePinService.kt:211-268`). REST для не-участника эти поля режет
  (`EventMapper.redactForOutsider`, PR #166), а чат отдаёт всем читателям группы, включая не-участников
  клуба; у публичной супергруппы — всем. Модель «чат = доверенная аудитория» это допускает
  (`club-chat-link.md:947,951`). Стоит одной строкой зафиксировать в спеке.
- **Любой участник группы (не админ) может добавить бота и стать владельцем клуба поверх чужого чата**
  (решение PO 2026-08-17, `ChatLinkBotService.kt:166-236`); посты сборов включаются сразу и не требуют
  админ-прав → канал для спама в группу, данных не раскрывает.
- **Карточка организатора** (`GET /api/clubs/{id}/organizer-card`) — любому с JWT без членства:
  `@username` владельца, аватар, число его клубов, суммарное число участников. «Организатор —
  публичный хост».
- **`@username` участника виден всем участникам клуба** (`MemberService.kt:115`), при этом в списке
  откликов на встречу он скрыт от не-менеджера (`VoteService.kt:142`). Несогласованно, но второй
  гейт обходится открытием карточки — дизайн-вопрос.
- **Оракул существования клуба** в `/start@bot <uuid>` в чужом чате: «Клуб не найден» vs «только
  владелец». UUID клубов и так публичны в deep-link.
- **localStorage общий между аккаунтами Telegram на одном устройстве**: город, флаги, список UUID
  клубов. JWT — только в памяти. Не ПДн.
- **Фронт пишет тело 401 в консоль и показывает сырой `error.message` JS-исключений** —
  безвредно, ПДн нет.

## 3. Проверено и в порядке

- **Авторизация REST**: долги (`requireAsDebtor/Creditor/Payee`, пара → 404 без общих долгов), сборы
  (hidden → 404, членство, `debts` только создателю, `paymentLink` только участникам), встречи
  (`redactForOutsider` на сервере, менеджерские поля за `MANAGE_EVENTS`), клуб (реквизиты и
  `chatInviteLink` только с доступом, два инвайт-кода разданы верно), участники (Trust чужих = null,
  frozen/expired не отдаются обычному участнику), заявки, биллинг (`@RequiresMembership/Organizer`,
  Robokassa ResultURL — allowlist IP + подпись), chat-link (`requireOwner`), статистика/финансы/награды
  за капабилити. `telegramId` — только в `/api/users/me`.
- **Бот**: реквизиты/телефоны/репутация/чеки в группу не идут; тихий сбор не постится и не
  напоминается; после срока у `shared` — только число; в группах только url-кнопки, callback'и
  проверяют `from.id` теми же гейтами, что REST; `/start` в группе при отказе молчит, payload не
  логируется; deep-link'и режутся сервером; привязка чата — только владелец, переезд
  group→supergroup по ответу Telegram; отчёт админам — агрегаты без ПДн.
- **Ошибки/инфра**: стектрейсов и SQL в ответах нет; `/actuator` снаружи недостижим (бэк не в сети
  Coolify, nginx проксирует только `/api/`); swagger/h2/devtools нет; стаб-оплата по
  `@ConditionalOnProperty`, dev-обход HMAC только по профилю; в бандл уезжают лишь публичные ключи
  Яндекс-карт и имя бота; source maps не собираются; CORS не открыт; initData/JWT/токен/пароли
  Robokassa не логируются; CI-секреты не печатаются.
- **Фронт**: JWT в памяти, persist-кэша нет; аналитики/Sentry нет; геокодер/саджест через бэк;
  `dangerouslySetInnerHTML`/`innerHTML` отсутствуют; пользовательских URL в `href` нет; deep-link'и
  парсятся строгими regex; `VITE_MOCK_INIT_DATA` в прод не попадает; скрытые экраны этапа 1 — данные
  за ними гейтятся бэком. Все роль-зависимые поля, которые фронт прячет, сервер зануляет —
  через DevTools лишнего не достать (таблица поле → гейт сверена).
