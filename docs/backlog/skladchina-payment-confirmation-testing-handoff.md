## 2. Модель, которая получилась (решения PO, не переоткрывать)

**«Я оплатил» — это заявка, а не деньги.** Участник заявляет оплату (`paid`), организатор
сверяет её с выпиской: «Засчитать» → `payment_confirmed`, «Не дошёл» → `payment_rejected`.
Массовая кнопка «Засчитать всех (N)» — то же решение оптом.

**Сбор закрывается ровно двумя способами:**

1. подтверждённые деньги добили цель (допуск 3 ₽, тот же, что у итогового статуса);
2. организатор нажал «Закрыть сбор» — «закрыть как есть»: неразобранные заявки становятся
   нейтральными, денег в итоге нет, минусов ни у кого.

Срок и «все ответили» закрытием **не** считаются — они лишь зовут организатора разобрать оплаты
(DM «сверьте деньги», один раз на сбор). Предохранитель: сбор, до которого организатор не дошёл
неделю после срока, закрывается **нейтрально** (молчуны и неразобранные заявки → `released`,
подтверждённое им до этого засчитывается).

**Спор.** Отклонённый участник может прислать **фото или скриншот чека** (PDF и произвольные
файлы не принимаются) в течение **48 часов**; пока спор открыт, −40 не списывается. Решает тот же
организатор: засчитал → +10, отказал → −40 и повторно оспорить нельзя. Спор, который никто не
разобрал **7 дней**, закрывается нейтрально.

**Репутация начисляется только при закрытии сбора.** Пока сбор идёт, решение организатора можно
переиграть сколько угодно раз. Отложенные исходы (−40 за неоспоренное отклонение, ноль за
протухший спор) добивает шедулер, и только по закрытым сборам.

**Прогресс — две доли:** зелёная (сверено) слева, серая (заявлено, ждёт сверки) хвостом. Отмена
участником или отклонение организатором убирают свой кусок серого. Так же в чате клуба:
`🟩` сверено · `🟨` заявлено · `⬜` не оплачено, плюс строка «💵 Собрано X из Y ₽».

**Наличные** («получил наличкой») сразу становятся подтверждённой оплатой — организатор
пересчитал деньги руками. Снять такую отметку он может (`unmark`), участнику ничего не приходит.

## 3. Статусы участника (глоссарий)

| Статус | Смысл | Репутация |
|---|---|---|
| `pending` | не ответил | −40 при закрытии после срока (`expired_no_response`) |
| `paid` | заявил оплату, организатор ещё не сверил | нет (промежуточный) |
| `payment_confirmed` | организатор сверил — деньги дошли | **+10** при закрытии |
| `payment_rejected` | платёж не найден, открыто окно на чек | **−40** через 48 ч без чека |
| `payment_disputed` | чек прислан, ждёт решения организатора | заморожено |
| `declined` / `released` | отказался / решения не потребовалось | строки нет |

`released` теперь получают и заявки, которые организатор не разобрал к закрытию.

Новые эндпоинты: `POST /api/skladchinas/{id}/unmark-paid` (участник снимает свою отметку),
`/confirm-all` (засчитать все заявки), `/dispute-payment` (чек),
`/participants/{userId}/resolve-payment` (решение организатора по оплате — и по ходу, и по чеку).
`POST /close` остался и означает «закрыть как есть».

## 4. Что тестировать на staging

Staging: **https://staging.77-42-23-177.sslip.io**
Подготовка данных: `./scripts/complete-event.sh --event "<название>" --yes` доводит встречу до
«явка отмечена», после чего по ней создаётся сплит («Разделить счёт»).

1. **Заявка и её отмена.** Участник жмёт «Я оплатил» → «⏳ Вы отметили оплату», кнопка «Отменить
   отметку» возвращает в «ожидает». Полоса теряет серый кусок.
2. **Сверка по ходу.** У организатора в строке — «Засчитать» и «Не дошёл». Засчитал → доля
   позеленела. Решение можно переиграть: «Не дошёл» после «Засчитать» и обратно.
3. **Закрытие по цели.** Подтвердить оплаты так, чтобы сумма добила цель, — сбор должен закрыться
   **сам**, без кнопки.
4. **Сбор не закрывается раньше времени.** Один отказался, оплата второго подтверждена, но денег
   меньше цели → сбор активен; закрывается только кнопкой «Закрыть сбор» (диалог предупреждает
   про неразобранные заявки).
5. **Отклонение и чек.** «Не дошёл» → участнику DM со сроком и причиной, на экране — загрузка
   чека и текст «Без чека оспорить нельзя». Приложил → «⏳ Чек отправлен», организатору DM,
   у него в строке виден сам чек и две кнопки. «Засчитать» → +10; «Платежа нет» → −40 и повторный
   спор запрещён.
6. **«Засчитать всех»** на сборе с несколькими заявками — одна кнопка вместо N тапов.
7. **Живой статус в чате** (нужен клуб с привязанным чатом): полоса из 10 квадратов, строка
   «Скинулись N из M · сверено K» и «Собрано X из Y ₽».
8. **Форма создания сбора** — плитки участников без пустых зазоров (был баг с отступами).
9. **Бейдж «Требует действия»** в табе «Сборы»: у отклонённого карточка подсвечена «Нужен чек»,
   даже когда сбор уже закрыт.

**Ускорение окон** (staging БД: `~/clubs-db.sh staging` → `localhost:15433`, DBeaver):

```sql
-- окно на чек истекло → следующий тик спишет −40 (только по ЗАКРЫТОМУ сбору)
UPDATE skladchina_participants SET payment_rejected_at = NOW() - INTERVAL '49 hours'
WHERE skladchina_id = '<id>' AND user_id = '<id>';

-- спор протух (7 дней) → участник уходит в released без минуса
UPDATE skladchina_participants SET disputed_at = NOW() - INTERVAL '8 days'
WHERE skladchina_id = '<id>' AND user_id = '<id>';

-- сбор брошен организатором (неделя после срока) → нейтральное закрытие
UPDATE skladchinas SET deadline = NOW() - INTERVAL '8 days' WHERE id = '<id>';

-- позвать организатора сверять заново (сбросить штамп DM)
UPDATE skladchinas SET confirmation_requested_at = NULL WHERE id = '<id>';
```

Три тика шедулера (`SkladchinaScheduler`: зов к сверке, нейтральное закрытие, добивание исходов)
ходят **раз в 10 минут** — после SQL нужно подождать или перезапустить бэкенд.

## 5. Открытые вопросы и следствия

1. **−40 за молчание зависит от организатора.** Раз срок больше не закрывает сбор, штраф
   молчунам появляется только при закрытии (по цели или рукой). Не закроет неделю — нейтральное
   закрытие спишет молчание в ноль. PO об этом сказано; если решит, что срок должен наказывать
   независимо, правка небольшая — вернуть тик закрытия по дедлайну.
2. **Сумма сбора теперь видна в чате клуба.** Раньше деньги в чат намеренно не светили; PO
   попросил больше информации. Кто сколько внёс — по-прежнему только у организатора.
3. **Мокап 6 (экран сверки с галками) устарел** — реализован другой путь, сам файл не правился.
4. **Нумерация миграций.** Занят номер **V89**. На локальной незапушенной ветке
   `feature/sprint-1.0-day4-payment-model` лежат V87/V88 (биллинг) — их придётся перенумеровать
   в V90/V91, иначе Flyway упадёт на out-of-order после мержа этой ветки.
5. **Валидация ссылки на чек** вынесена в `common/util/UploadedImageUrls.kt` (общая с чеком
   клубного взноса) и заодно стала принимать WebP. В форме взноса выбор файлов не менялся —
   там по-прежнему JPEG/PNG по решению PO от 2026-08-11.

## 6. Ловушки этой сессии

- **Тестам нужен Docker** (Testcontainers). Падение с `DockerClientProviderStrategy` означает,
  что Docker Desktop не запущен: `open -a Docker`.
- **Кодоген jOOQ** — по рецепту `branch-handoff-de-stars-member-admin.md` § 7 (временный PG на
  5433, миграции `sort -V`, `DB_URL=… ./gradlew generateJooq --rerun-tasks`). Локальная dev-БД
  отстаёт (была на V76) — на неё миграции не накатывать.
- **`ALTER TYPE … ADD VALUE` ломает exhaustive `when`** — компилятор показал ровно два места
  (`ReputationPolicy.financeKind` и конструктор `Skladchina`); верить компилятору, не LSP.
- **Не править файлы во время `./gradlew test`** — прогон подхватывает полуготовые классы и
  сыплет десятками ложных падений.
- **Фронт: чистый `tsc`** — перед проверкой `rm -f node_modules/.tmp/tsconfig.tsbuildinfo`.
- **msw ESM-флейк**: `ChatSetupGate.test.tsx` иногда падает в общем прогоне с
  `React.createContext is not a function`, изолированно зелёный. Окружение, не код.
- **Коллизия CSS-классов**: `.rd-pick-row` занят пикером активностей, форма сбора использует
  `.rd-pick-member`. Новые классы проверять на существование в `redesign.css`.
