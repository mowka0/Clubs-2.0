# Срез 2: подбор клубов по интересам

**Статус:** not-started · **Создано:** 2026-08-01 · **Origin:** проектная сессия по темам клуба.
**Предпосылка:** срез 1 ([`docs/modules/club-interests.md`](../modules/club-interests.md)) — разметка,
показ и поиск по темам — реализован в ветке `feature/club-interests`.

## Что уже есть после среза 1

- `interests.category` — тема знает свою полку;
- `club_interests (club_id, interest_id, position)` — клуб размечен темами (0–7);
- `interests.club_usage_count` — насколько тема ходовая у клубов (отдельно от `usage_count` профилей);
- `user_interests` — интересы человека (с V16);
- поиск каталога умеет искать по темам.

То есть **обе стороны сопоставления существуют** — это и было главным блокером. Раньше у клуба
не было ничего, с чем сравнивать интересы профиля.

## Чего не хватает

Рекомендаций нет вообще — ни одного эндпоинта. Утверждение в
[`onboarding-interests-and-recommendations.md`](onboarding-interests-and-recommendations.md)
про «recommendations сейчас работают по geo-match (MVP)» **неверно**: такого кода в проекте нет
(проверено 2026-08-01). Пустые экраны показывают лиса-маскота.

## Формула подбора

Никакого ML — объяснимая арифметика поверх сортировки, которая уже написана в `findAll`:

```
score = Σ по совпавшим темам вес(тема)
      × множитель города        ← решающий: клуб офлайновый
      + сигнал живости          ← recentActivity, уже считается
      + живой счёт участников   ← liveMemberCountField, уже считается
```

**Вес темы = редкость.** Совпадение по «сплавам» говорит о человеке больше, чем по «музыке».
Классический idf: `вес = 1 / log(1 + club_usage_count)` — колонка для этого уже есть.

**Город — множитель, а не слагаемое.** Клуб в другом городе бесполезен независимо от того,
насколько совпали темы: человек туда не поедет. Кандидаты не из города пользователя либо
отсекаются, либо получают множитель много меньше единицы.

## Холодный старт — главный риск

Пока клубов мало, у человека 5 интересов, а в его городе 3 клуба, пересечений будет **ноль**.
Полка «По твоим интересам» окажется пустой, и это читается как поломка, а не как «пока нечего
показать».

Поэтому деградацию закладывать **сразу**, а не потом:

| Уровень | Условие | Заголовок полки |
|---|---|---|
| 1 | Есть совпадения по темам | «По твоим интересам» |
| 2 | Совпала только полка (категория) | «Может быть интересно» |
| 3 | Только город + живость | «Рядом с тобой» |
| 4 | Ничего — общий каталог | полка не показывается вовсе |

Заголовок меняется вместе с уровнем — иначе полка врёт про то, чем она является.

## Где показывается

1. **Пустой экран Активностей** — сейчас там `FoxEmpty`; рекомендации дополняют, а не заменяют лиса.
2. **«Мои клубы» у новичка** — блок «Рекомендуем» (см. [`myclubs-recommended-clubs.md`](myclubs-recommended-clubs.md)).
3. **Каталог** — полка над общей выдачей.

## API (черновик)

```
GET /api/users/me/recommended-clubs?context=events_feed|my_clubs|discovery&limit=5
→ { level: "interests" | "category" | "city" | "none", clubs: ClubListItemDto[] }
```

`level` возвращается сервером, а не выводится клиентом: заголовок полки обязан соответствовать
тому, как список реально построен.

## Открытые вопросы

- **R-1.** Сбор интересов в онбординге — возвращать ли? В PR #133 онбординг сознательно сделан
  без вопросов («клубов нет, подбирать не из чего»). С появлением клубов вопрос открывается
  заново, но отдельным решением PO. Заготовка `user_categories` из отменённой
  `V60__onboarding_taxonomy.sql` (коммит `947b3be`) ждёт там же.
- **R-2.** Приватность: закрытые клубы в рекомендациях — да (они видны в каталоге), приватные — нет.
  Совпадает с фильтром `findAll`, отдельного решения не требует, но тест нужен.
- **R-3.** Анти-фарм: организатор может разметить клуб семью популярными темами, чтобы лезть во все
  выдачи. Idf это частично гасит (популярная тема весит мало), но стоит подумать про потолок.
- **R-4.** Пересчёт на лету или кэш? На текущих объёмах — на лету; при росте вынести в
  материализованную таблицу, как `club_rank`.
