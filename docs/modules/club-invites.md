# Приглашения в клуб + механика полного клуба (club-invites)

> Статус: **as-built** — реализовано и принято PO на staging 2026-07-11.
> Мокапы: `docs/design/club-invites/mockups/01-invite-flow.html` (путь инвайта, кадры A–E)
> и `02-full-club.html` (полный клуб, кадры F–I).
> Пререквизит выполнен: `telegrambots` 9.5.0 в master (#106), `rawApiCall` снесён.

## Зачем

Организатор зовёт людей в клуб лично: выбирает получателей в **нативном пикере Telegram**,
приглашение уходит **от его имени** (не от бота — бот не может писать незнакомцам и не видит
контакты). Получатель открывает карточку клуба в Mini App и вступает в один тап.
Вторая половина — механика полного клуба: «хочу вступить, а мест нет» превращается в заявку,
которую орг разруливает из инбокса, расширяя клуб.

## Решения PO (2026-07-11)

1. **Вступление по инвайту — сразу член** (существующий `joinByInvite`), без заявки.
   В платном клубе «сразу член» = `frozen` до подтверждения взноса — как везде.
2. **Клуб полон** — инвайт и витрина деградируют в обычную заявку («Попроситься в клуб»).
   В инбоксе орга заявки полного клуба собираются в один блок: крестик отсеивает лишних
   (обычный отказ с причиной), поле нового лимита (подсказка — текущий лимит числом),
   кнопка **«Расширить клуб и принять всех (N)»** — атомарно.
3. **Платный клуб** — текущее поведение: цена видна на посадочной, после вступления/одобрения
   участник `frozen`, платит оргу напрямую, орг подтверждает взнос.
4. **Текст приглашения** — фиксированный шаблон, орг своё не дописывает.
5. **Кто приглашает** — владелец и роль `organizer`.
6. **Бейдж «по вашему приглашению»** — отклонён, заявки без пометки источника.
7. **Механика отправки — prepared message** (rich-карточка с кнопкой). Фолбэк для старых
   клиентов без `shareMessage` — «Скопировать ссылку».

## Ключевой инвариант (платные клубы)

**Оплата доступна только membership'у в статусе `frozen` — заявитель платить не может физически**
(экран взноса живёт в membership-флоу, заявка membership не создаёт). Поэтому сценарий
«оплатил, а заявку отклонили» исключён порядком шагов: заявка → одобрение → `frozen` → оплата.

Матрица флоу:

| Ситуация | Флоу |
|---|---|
| Открытый платный, есть места | вступил сразу → `frozen` → платит → орг подтвердил |
| По заявке (`closed`), есть места | заявка → approve → `frozen` → платит |
| Любой клуб, мест нет | «Попроситься» → блок в инбоксе → «Расширить и принять» → `frozen` → платит |
| Личный инвайт, есть места | сразу член (`frozen` в платном) → платит |
| Личный инвайт, мест нет | как «Попроситься» |

Лимит мест считает `active + frozen + expired` (существующий `countActiveByClubId`) — не меняем.

## Часть 1. Личные приглашения

### Инвайт-код: расширение на все типы клубов

Сейчас `clubs.invite_code` генерится только при создании `private`-клуба; у `open`/`closed` — NULL.
Новое: код нужен любому клубу — **ленивая генерация**: эндпоинт шаринга (см. ниже) создаёт код,
если его ещё нет (существующий `generateInviteCode()`). Миграция не нужна.
Семантика `private` не меняется (не виден в каталоге, вход только по ссылке).
Регенерация кода — существующий `POST /api/clubs/{id}/regenerate-invite` (менеджер: владелец /
активный со-организатор, см. `co-organizers.md`), отзывает старую ссылку.

### Новый эндпоинт шаринга

```
POST /api/clubs/{id}/invite-share            (ЛЮБОЙ участник клуба со `status = active`; владелец — всегда)
→ 200 { "inviteUrl": "https://t.me/<bot>?startapp=invite_<code>",
        "preparedMessageId": "<id>" }
```

- Гарантирует наличие invite-кода (ленивая генерация).
- Вызывает Bot API `savePreparedInlineMessage` для `telegram_id` вызывающего:
  карточка-приглашение (InlineQueryResultArticle, HTML) с текстом по кадру C —
  «**Приглашаю тебя в мой клуб!**» у менеджера / «**Приглашаю тебя в наш клуб!**» у обычного
  участника (роль решает притяжательное: у участника клуб не «мой») + blockquote-«карточка»
  (название, категория · город · N участников) + сниппет описания (до 120 символов) +
  «Посмотри и вступай 👇» — и inline-кнопкой **«Открыть клуб»** → `inviteUrl`. Имени
  приглашающего в тексте нет — он и есть отправитель. Все четыре `allow*`-флага обязательны
  (@NonNull в библиотеке): люди и группы true, боты и каналы false.
- `preparedMessageId` живёт недолго и **одноразовый** — фронт запрашивает при каждом
  открытии шита и после каждой отправки (серийная отправка: «Отправить ещё», см. ниже).
- 403 — не участник клуба либо участник без доступа (`frozen` / `expired` / вышедший);
  404 — клуба нет.

> **Кто может приглашать — изменено 2026-07-30 (решение PO).** Раньше гейтом была капабилити
> `SEND_INVITES` (владелец / активный со-организатор). Теперь звать может **любой участник
> клуба**: гейт совпадает с гейтом ростера (`MemberService.getClubMembers`) — кто видит состав,
> тот и приглашает. Капабилити переименована в `MANAGE_INVITE_LINK` и гейтит только
> **перегенерацию** ссылки (отзыв старой) — это по-прежнему менеджерское действие.
>
> **Заявка при входе по приглашению — сделано 2026-07-30 (V71).** Раньше инвайт-код был один на клуб
> и `POST /api/invite/{code}/join` вступал НАПРЯМУЮ при любом `accessType` — в клубе «по заявке»
> приглашённый входил без одобрения организатора. Теперь у клуба **два кода** (см. § ниже).

### Два инвайт-кода: заявочный и прямой (V71)

| Кто копирует/отправляет | «Отправить в Telegram» | «Скопировать ссылку» |
|---|---|---|
| Менеджер (владелец / со-орг) | заявочный код → **заявка** | прямой код → **сразу в клуб**, кнопка подписана предупреждением |
| Обычный участник | заявочный код → **заявка** | заявочный код → **заявка** (обхода ему не дают) |

- `clubs.invite_link` — **прямой** код (вход мимо заявки), `clubs.apply_invite_code` — **заявочный**
  (V71, ленивая генерация как у прямого). Оба уникальны, оба резолвятся в `GET /api/invite/{code}`.
- **Почему два кода, а не флаг в ссылке.** Будь код один, разница жила бы в параметре deep-link'а,
  и получатель «заявочной» ссылки обошёл бы одобрение, стерев параметр. Из заявочной ссылки прямой
  код не вывести — правило неподделываемо.
- В `closed`-клубе `POST /api/invite/{applyCode}/join` отвечает **400** («нужно отправить заявку»):
  проверка живёт в `MembershipService.joinByInviteCode`, а не только на посадочной, иначе правило
  обходилось бы прямым вызовом эндпоинта.
- В `open` / `private` одобрения не существует, поэтому там оба кода ведут себя одинаково
  (прямое вступление), а `linkBypassesApproval` = false — подписывать нечего.
- `ClubDetailDto.inviteLink` (прямой код) с 2026-07-30 отдаётся **только менеджеру**
  (`includeInviteLink` в `ClubMapper.toDetailDto`). Иначе правило «обычный участник не может дать
  ссылку в обход заявки» обходилось бы чтением кода из ответа `GET /api/clubs/{id}`; посадочная
  приглашения его тоже не отдаёт. Фронтенд это поле не читает — оно нужно ответу на регенерацию.
- `InviteShareDto.linkBypassesApproval` — фронтенд подписывает им кнопку копирования: «клуб
  принимает по заявке, но по этой ссылке вступают сразу — этап одобрения пропускается».
- `ClubDetailDto.inviteRequiresApplication` (только в ответе `GET /api/invite/{code}`) — посадочная
  по нему рисует «Отправить заявку» вместо «Вступить в клуб» и поле вопроса организатора.

### Фронт: половина приглашающего

| Место | Что |
|---|---|
| `ClubPage`, таб «Участники» | строка-кнопка «＋ Пригласить в клуб» над ростером, видна **любому участнику**, кто видит состав (кадр A) |
| Боттом-шит `InviteSheet` (кадр B) | строки-опции: «Отправить в Telegram» → `shareMessage(preparedMessageId)`; «Скопировать ссылку» → `inviteUrl` в буфер; внизу «Отмена». Если `shareMessage` недоступен или prepared не создался — остаётся только копирование |
| Серийная отправка | пикер Telegram даёт выбрать ОДИН чат за раз (ограничение платформы) — после отправки шит остаётся открытым, готовит свежий prepared message и показывает «Отправить ещё · Отправлено: N ✓» |
| Успех создания клуба (кадр E) | экран «Клуб «…» создан 🎉» в модалке создания: «Пригласить участников» (клуб откроется с открытым шитом, `state.openInvite`) / «Позже» |
| `DeepLinkHandler` | новый префикс `invite_<code>` → `/invite/<code>` (по образцу `club_`/`event_`) |

### Посадочная приглашённого

`/invite/:code` (`InvitePage`). **С 2026-07-30 — та же композиция, что видит гость на странице
клуба** (решение PO): приглашение показывает тот же объект, и две разные вёрстки означали бы, что
человек до и после вступления видит как будто разные продукты. Бэкенду для этого не потребовалось
ничего: `GET /api/invite/{code}` и раньше отдавал полный `ClubDetailDto` (обложка, правила, район,
чат), а блоки качества и афиши грузятся по `clubId` и публичны.

Порядок экрана:
1. **`ClubIdentityHeader`** — обложка → аватар на стыке → название → чипы «доступ · город ·
   состав · взнос». Общий компонент со страницей клуба (`components/club/ClubIdentityHeader.tsx`);
   в угол обложки вместо кнопок роли уходит метка «✉ Приглашение» (`.rd-invite-badge`).
2. **Строка организатора** (`.rd-invite-org`) — кружок с инициалом + «Организатор — <имя>» и
   подпись: «взнос вы передаёте напрямую, минуя платформу» в платном клубе, иначе «отвечает за
   клуб и встречи». Раньше имя стояло серой сноской ПОД кнопкой.
   > В ответе лежит имя **владельца** (`ClubService.getClubByInviteCode`), а ссылку с 2026-07-30
   > может прислать любой участник — код общий на клуб и отправителя не знает. Поэтому подпись
   > говорит «организатор», а не «вас зовёт <имя>». Персональное «зовёт Маша» потребует
   > параметра-отправителя в ссылке — отдельная задача, см. `docs/backlog/invite-screen-and-club-preview.md`.
3. **Чип «🌱 Клуб только собирается — вы будете одним из первых»** (`.rd-cl-chip.rd-accent`) —
   когда `totalMeetings === 0` И `memberCount <= 5` (`FIRST_MEMBERS_THRESHOLD`). Закрывает крайний
   случай молодого клуба: блоки качества и афиши у него fail-soft молчат, и без этой строки экран
   схлопывался бы к голому описанию.
4. **«О клубе»** (`.rd-club-about`) — описание + правила (`rules` приходили в ответе, но не
   выводились) + пилюля «💬 В чат», см. ниже.
5. **`ClubQualityFacts`** («Жизнь клуба») и **`ClubEventsTeaser`** («Афиша клуба») — те же
   публичные блоки, что у гостя на странице клуба. Афише строка-замок НЕ передаётся: то же самое
   говорит плашка сразу под ней.
6. **`ClubLockedNotice`** — «Активности клуба доступны участникам».
7. **CTA** — «Вступить в клуб» = `POST /api/invite/{code}/join` (сразу член; `frozen` в платном).
   В платном клубе кнопка называется **«Вступить и оплатить взнос»** и под ней: «Дальше выберете
   способ — СБП или наличными. Взнос вы передаёте организатору напрямую, платформа денег не
   касается и ничего не списывает» (главный страх платного приглашения: «Вступить» читается как
   «заплатить»).

### Один экран вместо трёх (решение PO 2026-07-30)

Платный путь стоил **5 тапов и 3 экрана**: «Вступить» → экран «Добро пожаловать» → «Перейти в
клуб» → страница клуба → «Оплатить взнос» → шит. Два экрана из трёх не несли ни одного решения.
Теперь взнос предлагается на самой посадочной:

- тап по «Вступить и оплатить взнос» → `join` → `DuesPaymentSheet` открывается здесь же.
  Реквизиты СБП приходят только участнику, поэтому после вступления страница дозапрашивает
  `GET /api/clubs/{id}` (мутация вступления инвалидирует кэш деталей — иначе шит получил бы
  гостевой ответ с пустым `paymentLink`);
- **закрыть шит, не заплатив, — не тупик:** человек уже участник, экран говорит «Взнос можно
  передать позже» и держит обе кнопки («Оплатить взнос» / «Перейти в клуб»). Кнопка не обманывает:
  вступление действительно происходит по тапу;
- после claim — «Оплата на проверке» + «Перейти в клуб»;
- **новичку велком-сцена показывается ПОСЛЕ оплаты**, а не между решением и деньгами;
- **бесплатный клуб уже-онбордженному** — сразу `/clubs/{id}`, экран-подтверждение снят (он
  существовал ради одной кнопки). Новичку по-прежнему велком-сцена;
- **должник** (`frozen`/`expired`), открывший приглашение в свой же клуб, получает первой кнопкой
  «Оплатить взнос» (тот же шит на месте) и «Перейти в клуб» второй. Раньше ему предлагали только
  дверь в клуб, хотя мы уже знали, что он должен взнос.

Связанное правило по DM — `telegram-bot.md` § `?pay=1`.

Ветки CTA:
- **по заявочному коду в `closed`-клубе** — поле вопроса организатора (если задан) и кнопка
  «Отправить заявку» → `POST /api/clubs/{id}/apply`, подпись «Организатор посмотрит заявку и
  откроет доступ»; после отправки экран «Заявка отправлена»;
- **клуб полон** — чип «👥 В клубе кончились места…» + «Попроситься в клуб» (часть 2, кадр G);
  после подачи — «Заявка отправлена» с кнопкой «К списку клубов»;
- **уже участник** (active/frozen/expired) — «✓ Вы уже состоите в этом клубе» + «Перейти в клуб»
  вместо CTA (отфильтровать получателя в нативном пикере нельзя — пикер не сообщает выбор
  приложению; бэкенд повторное вступление отбивает 409).

Снято как дублирующее (решение PO 2026-07-30): чип «✋ Клуб принимает по заявке…» (то же говорят
чип «По заявке» в шапке и подпись под кнопкой), строка-замок под афишей (то же говорит плашка) и
чип «💬 У клуба есть чат…» (заменён пилюлей в «О клубе»).

Дополнения к контракту `GET /api/invite/{code}`: в `ClubDetailDto` добавляется имя владельца
(`ownerFirstName`, `ownerLastName`), а с 2026-07-30 заполняются публичные чат-поля
`chatLinked` / `chatDoorEnabled` — раньше метод звал маппер без них, и ответ всегда говорил
«чата нет» (`chatInviteLink` по-прежнему null: эндпоинт не знает вызывающего).

**Взаимодействие с онбордингом (2026-07-13, дополнено 2026-07-24).** Приглашённый впервые открывает
мини-апп по deep-link, то есть с непустым `startParam` — карусель первого входа тогда **откладывается**:
он шёл к конкретным людям, а не знакомиться с продуктом, и попадает сразу на посадочную. Правило шире,
чем «только инвайт»: любой deep-link (`club_`, `event_`, складчина) откладывает онбординг так же.
**С 2026-07-24** новичок после вступления видит не сухое «Добро пожаловать», а **велком-сцену**
(онбординг срез 3, кадры A/B) — она и помечает `onboarded_at`, так что карусель ему больше не
показывается. Полный клуб → заявка: сцена `applied` (кадр C), `onboarded_at` НЕ помечается — при
следующем обычном запуске карусель покажется. Уже-онбордженным остаются прежние экраны
(«Добро пожаловать» / «Заявка отправлена»). См. [`onboarding.md`](./onboarding.md) § «Срез 3».

## Часть 2. Полный клуб

### Подача заявки в полный клуб

`submitApplication` сейчас требует `accessType == closed`. Ослабляем:

```
заявка принимается, если accessType == closed  ИЛИ  клуб полон (любой тип)
```

Всё остальное без изменений: дедуп активной заявки, rate limit 3/день, вопрос клуба
(для open-клуба вопроса обычно нет — `answerText` не требуется), DM оргу о новой заявке
(в текст добавляется «клуб полон» при полноте).

### Фронт: витрина и посадочная

- `ClubPage` (посетитель) и `InvitePage`: если `memberCount >= memberLimit` — баннер
  «Клуб сейчас полон» + CTA **«Попроситься в клуб»** → `submitApplication` (кадры F, G).
- После подачи — обычное состояние «заявка отправлена» (существующие «Мои заявки»).

### Инбокс орга: блок полного клуба (кадры H, I)

Группировка — **чисто фронтовая**: `useMyPendingApplicationsQuery` уже отдаёт заявки с
`ClubBriefDto`; заявки клубов, где `клуб полон`, собираются в блок по клубу
(нужно знать `memberCount`/`memberLimit` клуба — добавить оба поля в `ClubBriefDto`).

- Шапка блока: аватар + название + «N заявок» + пилюля «Клуб полон · X/X».
- Строка заявителя: имя + краткий peerStats; крестик (квадратный, r=9) = **существующий
  reject-флоу** с обязательной причиной и DM заявителю.
- Футер: поле «Новый лимит участников» (подсказка-плейсхолдер — текущий лимит числом),
  строка-калькулятор «мест X, заявок N — чтобы принять всех, укажите не меньше X+N»,
  кнопка «Расширить клуб и принять всех (N)».
- Заявки НЕполных клубов — отдельными карточками, как сейчас.
- После расширения блок рассыпается в обычные карточки автоматически (клуб больше не полон).

### Новый эндпоинт: расширить и принять атомарно

```
POST /api/clubs/{id}/expand-and-approve      (менеджер: владелец / активный со-организатор — как approve)
{ "newMemberLimit": 23, "applicationIds": ["...", "..."] }
→ 200 { список ApplicationDto }
```

Одна транзакция:
1. менеджер-check (владелец / активный со-организатор — см. `co-organizers.md`); все заявки принадлежат клубу и в статусе `pending`;
2. `newMemberLimit > текущего лимита` и `newMemberLimit >= countActiveByClubId + applicationIds.size`;
3. обновить `member_limit`;
4. одобрить каждую заявку той же логикой, что `approveApplication`
   (платный клуб → `frozen`, бесплатный → `active`; DM «заявка одобрена / оплатите вступление»).

DM-ки шлются после коммита (best-effort, как в существующем approve).

## Вне скоупа (осознанно)

- Пометка источника заявки «по приглашению» (решение PO №6).
- «Принять всех» без расширения; батч-approve для неполных клубов.
- Nudge «в клубе 3 из 20 — пригласи своих» на странице клуба.
- Кастомный текст приглашения от орга.
- `requestWriteAccess` (отдельная задача, следующая по очереди).
- Мультивыбор получателей в пикере prepared message — невозможен на платформе
  (один чат за раз); вместо него серийная отправка. Вариант «нескольким сразу
  текстом» (share-ссылка без карточки) — обсуждён, PO решение не принял.

## Критерии приёмки

1. Строку «Пригласить в клуб» в табе «Участники» видит **любой участник клуба** — и менеджер,
   и обычный участник. Не-участник таба не видит вовсе; должник (`frozen`/`expired`) — тоже.
2. «Отправить в Telegram» открывает нативный пикер; получатель получает карточку от имени
   приглашающего с кнопкой «Открыть клуб»; кнопка ведёт на `/invite/<code>` в Mini App.
   Текст: «в мой клуб» от менеджера, «в наш клуб» от обычного участника.
2a. **Клуб «по заявке»:** приглашённый из Telegram видит «Отправить заявку», а не «Вступить»;
   прямой `POST /api/invite/{applyCode}/join` отвечает 400. Ссылка, скопированная **менеджером**,
   пускает сразу и подписана предупреждением; ссылка, скопированная **обычным участником**, ведёт
   на заявку — обход одобрения ему недоступен. В `open`/`private` обе ссылки пускают сразу.
2b. Прямой инвайт-код не приходит в `GET /api/clubs/{id}` никому, кроме менеджера, и не приходит
   на посадочной приглашения.
3. «Скопировать ссылку» кладёт в буфер рабочий deep-link (открывается с холодного старта).
4. Вступление по инвайту: бесплатный клуб → сразу `active`; платный → `frozen` + существующий
   взнос-флоу; посадочная показывает цену и имя орга.
5. Инвайт-ссылка работает для `open`, `closed`, `private` клубов; регенерация отзывает старую.
6. Полный клуб (любой тип): витрина и посадочная показывают «полон» + «Попроситься»;
   заявка попадает в инбокс; НЕполный open-клуб заявку по-прежнему не принимает.
7. Инбокс: заявки полного клуба сгруппированы в блок; отказ по крестику работает как обычный
   отказ (причина + DM); «Расширить клуб и принять всех» поднимает лимит и принимает
   оставшихся одной операцией; валидация лимита (п. 2 эндпоинта) отбивает 400.
8. После расширения: принятые в платном клубе — `frozen` с DM «оплатите»; в бесплатном —
   `active`; блок в инбоксе рассыпался.
9. Заявитель НЕ видит экран оплаты до одобрения (инвариант).
10. Регресс: обычные заявки в `closed`-клуб с местами работают как раньше.
