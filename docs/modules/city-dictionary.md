# Справочник городов (city-dictionary)

> Статус: **в разработке** — ветка `feature/city-dictionary`.
> Решения PO приняты 2026-07-31 в ходе проектной сессии.

## Зачем

Город задавался тремя разными способами, и один из них ничем не ограничивался:

| Место | Как вводился | Что уходило в БД |
|---|---|---|
| Профиль | `CityPicker` с хардкодом 34 городов | `country` = `'RU'` + `city` = `'Москва'` |
| Фильтр каталога | тот же `CityPicker` | `?city=Москва` |
| Создание клуба | **свободный `<input>`** | что угодно, валидация только `@NotBlank` |
| Управление клубом → Настройки | **свободный `<input>`** | то же самое, уже после создания |

Мест со свободным вводом оказалось два, а не одно: город можно было испортить и при создании
клуба, и потом в настройках. Вторая дыра обнаружилась при реализации — в первоначальном разборе
её не было.

Фильтр каталога сравнивал строки точно (`CLUBS.CITY.equalIgnoreCase`), поэтому клуб, созданный
как «мск», «Москва » или «Санкт Петербург», **не находился никогда**. Организатор при этом видел
его в «Управлении» и не догадывался о проблеме — клуб-призрак, тихая потеря без сигнала.

Дополнительно: у клуба вообще не было страны, поэтому одноимённые города разных стран
склеивались в одну выдачу.

## Решения PO (2026-07-31)

1. **Справочник в БД — единственный источник правды** для профиля, фильтра каталога и создания
   клуба. Город больше нигде не вводится текстом.
2. **Данные — статическая выгрузка GeoNames**, порог населения **50 000**, страны
   RU/BY/KZ/AM/GE/AE/TR. Итог — **540 городов**.
3. **Геокодер в рантайме отвергнут** как избыточный для MVP. Промежуточный вариант
   «справочник + Яндекс-геокодер как расширитель» рассматривался и **отменён**. Путь назад
   открыт: геокодер прикручивается поверх готового справочника без переделки схемы.
4. **Только города, без областей и прочих административных центров** — «Балашиха», «Реутов»,
   «Москва».
5. **Одноимённые города получают уточнение** (регион). Показывается только там, где без него
   не различить.
6. **Кнопки «добавить город» нет.** Нет города — человек выбирает ближайший крупный.

## Ключевой инвариант: денормализация только сверху вниз

`clubs.city_id` — источник правды, `clubs.city` остаётся текстовым полем **только для
отображения** и заполняется **исключительно сервером** из справочника по `city_id`.

Клиент прислать произвольный текст города не может физически: в запросах есть только `cityId`,
поля `city` в них нет. Поэтому расхождение между FK и текстом невозможно по построению, а
карточки и списки читаются без джойна.

## Схема БД (V74)

```sql
CREATE TABLE cities (
    id              UUID PRIMARY KEY,
    country_code    VARCHAR(2)  NOT NULL,
    name            VARCHAR(120) NOT NULL,
    normalized_name VARCHAR(120) NOT NULL,
    region          VARCHAR(120),
    needs_region    BOOLEAN NOT NULL DEFAULT FALSE,
    population      INTEGER NOT NULL,
    latitude        NUMERIC(9,6) NOT NULL,
    longitude       NUMERIC(9,6) NOT NULL,
    geoname_id      INTEGER NOT NULL,
    is_featured     BOOLEAN NOT NULL DEFAULT FALSE
);
CREATE UNIQUE INDEX idx_cities_country_normalized
    ON cities(country_code, normalized_name, COALESCE(region, ''));
```

**Регион входит в уникальный ключ намеренно.** Без него индекс запрещал бы ровно то, что мы
сознательно храним: Железногорск в Курской области и в Красноярском крае — разные города.
`COALESCE` нужен потому, что в уникальном индексе `NULL <> NULL`, и записи без региона иначе
задваивались бы свободно. Дубль внутри одного региона по-прежнему невозможен.

- `normalized_name` — ключ дедупликации и поиска: lower + `ё`→`е` + trim + схлопывание пробелов.
  **Дефис не убирается** («Ростов-на-Дону» ≠ «Ростов»).
- `needs_region` — у города есть тёзка в другом регионе той же страны, уточнение обязательно.
- `is_featured` — показывать в списке до ввода запроса (витрина, не происхождение данных).

`clubs.city_id` и `users.city_id` — **nullable** FK. Nullable намеренно: клуб с нераспознанным
легаси-городом не должен упасть, он просит организатора выбрать город при следующем входе.

## API

### `GET /api/cities`

Под JWT, как весь остальной `/api/**`: пикер открывается только у авторизованного человека
(профиль, создание клуба, каталог), публичной поверхности не добавляем. Отдаёт справочник целиком
одним ответом — 540 записей, ~40 КБ. Фронт кеширует через TanStack Query и фильтрует локально:
поиск идёт **без сети**.

```json
[{ "id": "…", "name": "Железногорск", "region": "Курская область",
   "needsRegion": true, "countryCode": "RU", "isFeatured": false, "hasClubs": false }]
```

`hasClubs` считается на лету и нужен витрине: до ввода запроса показываются featured-города плюс
те, где клубы уже есть. Координаты и население в ответ не идут — UI их не использует (YAGNI,
в БД лежат под будущее «клубы рядом»).

### Изменения существующих контрактов

| Контракт | Было | Стало |
|---|---|---|
| `GET /api/clubs?city=Москва` | строка, `equalIgnoreCase` | `?cityId=<uuid>`, сравнение по FK |
| `CreateClubRequest` | `city: String` (`@NotBlank`) | `cityId: UUID` (`@NotNull`, существование проверяет Service) |
| `UpdateClubRequest` | `city: String?` | `cityId: UUID?` |
| `UpdateMeRequest` | `city: String?`, `country: String?` | `cityId: UUID?` (страна приезжает из справочника) |
| `ClubDto` / `ClubListItemDto` | `city: String` | `city: String` **остаётся** + `cityId: UUID?` рядом |

`city` в ответах сохраняется намеренно — на нём висят карточки, шапки и DM-уведомления;
ломать их ради переименования поля незачем.

## Фронтенд

`CityPicker` перестаёт быть хардкодом и становится единственным способом задать город:

- список приезжает из `GET /api/cities`, вкладки стран строятся из данных;
- **поле поиска** фильтрует локально с первого символа по `normalized_name`;
- до ввода запроса показываются `is_featured` + города, где есть клубы; **поиск при этом идёт по
  всему справочнику** — иначе человек из города без клубов не найдёт себя в профиле;
- регион выводится второй строкой **только при `needsRegion`**; если регион совпадает с именем
  города (Москва, Санкт-Петербург — города федерального значения), показывается только страна;
- ничего не найдено → `FoxEmpty` «Не нашли такой город», без кнопок обхода.

Точки подключения — четыре: `ProfileEditModal` и `DiscoveryPage` (уже использовали пикер, переехали
на `cityId`), `CreateClubModal` и `OrganizerClubManage` → «Настройки» (**текстовый `<input>`
заменён на пикер**).

### Ловушка: пикер внутри модалки на vaul (баг PO 2026-08-01)

`CityPicker` рендерится **порталом в `body`**, то есть вне DOM-поддерева того окна, из которого
его открыли. Модалки на vaul/Radix (`CreateClubModal` в telegram-ui `Modal`) слушают `pointerdown`
на `document` и закрываются по клику снаружи — тап по списку городов был для них именно таким
кликом, и форма создания клуба закрывалась вместе с наполовину заполненными полями.

Корень — в том, что модалка **выключает указатель на всём остальном документе**:

Radix Dialog (под vaul, на нём же `Modal` telegram-ui) на время своей жизни ставит
`document.body.style.pointerEvents = 'none'` и возвращает `auto` только собственному контенту.
Пикер — портал в `body`, значение наследуется, и он оказывается **видимым, но некликабельным**:
тапы проходят сквозь него в оверлей модалки, та считает их кликом снаружи и закрывается вместе
с формой. Отсюда и ощущение PO «кликаю в пустоту». Лечится собственным `pointer-events: auto`.

Вторым слоем — порядок наложения:

- лист пикера несёт `role="dialog"`, и глобальное правило `[role="dialog"] { z-index: 1000
  !important }` поднимает его наверх — пикер видно и по нему можно попасть;
- **его затемнение (`.rd-sheet-overlay`) осталось на `z-index: 150`**, то есть ПОД оверлеем
  модалки-хозяйки (у той тоже 1000). Вся площадь вокруг листа принадлежала чужому оверлею:
  тап туда модалка считала кликом снаружи и закрывалась вместе с формой, а «прошедший
  насквозь» клик попадал уже в карточку под ней и уводил на другой экран (в логах бэкенда
  это выглядело как три параллельных `Club not found` — так грузится страница клуба).

Лечение — в самом пикере, три части:

1. `pointer-events: auto` на затемнении и листе — снимает наследование `none` от `body`;
2. классы `.rd-over-modal` / `.rd-over-modal-sheet` кладут их поверх любой шторки, из которой
   пикер открыт (`z-index: 1100 / 1101 !important`);
3. оверлей и лист гасят весь указательный цикл (`pointerdown` → `move` → `up`, их
   touch-двойники и `click`) — React-события всплывают по РЕАКТ-дереву, то есть доходят
   до модалки-хозяйки даже из портала в `body`.

Регрессия закрыта тестами `CityPicker.test.tsx` («тап не «протекает» наружу», «лежит поверх
модалки»).

То же правило действует для любого нового портала-шита, открываемого изнутри другой шторки:
поверх — значит и по z-index тоже, включая затемнение.

В настройках клуба, у которого `cityId` пуст (легаси-запись, не распознанная миграцией),
под полем показывается подсказка: «Город клуба не распознан — выберите его, иначе клуб не найдут
в каталоге». Это единственное место, где организатор узнаёт о проблеме и чинит её.

## Миграция легаси-данных

1. Матчинг `clubs.city` / `users.city` по `normalized_name` в пределах справочника.
2. Совпало — проставляется `city_id`, текст перезаписывается каноническим именем.
3. Не совпало — `city_id` остаётся `NULL`, текст **не трогается** (чтобы организатор видел, что
   было). Клуб продолжает работать, но в каталоге по городу не находится до уточнения.
4. Организатору с `city_id IS NULL` при входе в управление клубом показывается просьба выбрать
   город.

## Вне скоупа (осознанно)

- **Геокодер и добавление городов пользователями** — решение PO, см. выше.
- **`district`** остаётся свободным текстом: в фильтрации не участвует, унифицировать нечем.
- **«Клубы рядом» по координатам** — координаты в БД лежат, UI не делаем.
- **Пополнение справочника** — новой миграцией с пересобранным сидом; админки нет.

## Критерии приёмки

1. Клуб нельзя создать с городом вне справочника — поля свободного ввода в форме нет.
2. Клуб, созданный в городе X, находится фильтром «город X» — при любом регистре и написании,
   потому что сравнение идёт по FK, а не по строке.
3. Профиль позволяет выбрать любой из 540 городов; поиск находит город по первым буквам.
4. Железногорск в списке показан дважды с разными регионами; Москва — без региона.
5. Легаси-клуб с распознанным городом получает `city_id` и находится в каталоге.
6. Легаси-клуб с нераспознанным городом **не падает**, открывается, показывает просьбу уточнить.
7. `GET /api/cities` доступен без авторизации и отвечает 540 записями.
