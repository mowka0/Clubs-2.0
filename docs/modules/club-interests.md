# Темы клуба (club-interests) — срез 1

> Статус: **в разработке** — ветка `feature/club-interests`.
> Решения PO приняты 2026-08-01 в ходе проектной сессии.
> Срез 2 (рекомендации по интересам) — в [`docs/backlog/club-interests-recommendations.md`](../backlog/club-interests-recommendations.md).

## Зачем

Клуб описан ровно одной полкой из восьми (`clubs.category`). Этого мало сразу в трёх местах:

| Место | Что сейчас | Чем плохо |
|---|---|---|
| Поиск каталога | `LIKE '%запрос%'` по `name` + `description` | Клуб «Пятничные партии» по запросу «настолки» **не находится** — слова нет ни в имени, ни в описании |
| Карточка каталога | одна полка «Спорт» | Человек не понимает, бег там или бокс, не открыв клуб |
| Подбор клубов | не существует | Интересы в профиле собираются с V16, но у клубов нет ничего, с чем их сопоставлять |

Расширять сам список категорий — неверный ход: полка это навигация, и чем полок больше, тем
хуже каталог (пустые полки, нелистаемый фильтр). Вместо этого добавляется **второй уровень**.

## Решения PO (2026-08-01)

1. **Категория не меняется.** 8 полок, задаётся один раз при создании, остаётся фильтром и
   навигацией. `club_rank.category` и правило «один клуб владельца на категорию» не трогаются.
2. **Темы — второй уровень**, 0–7 на клуб. В отличие от категории, **темы редактируются**:
   ошибку разметки организатор должен уметь исправить, на ранг они не влияют.
3. **Словарь общий с профилем** — та же таблица `interests`. Смысл всей затеи в том, чтобы
   интересы человека и темы клуба лежали в одном пространстве имён; два отдельных словаря
   сопоставить было бы нечем.
4. **Темы не обязательны.** Создание клуба без тем не блокируется — трение в воронке создания
   дороже, чем идеальная разметка. Экран показывается всегда, чипы подталкивают.
5. **Внешний дамп (Wikidata / Википедия) отвергнут.** Для города правильность = совпадение с
   реальностью, для темы = совпадение со словами, которыми люди себя описывают. Wikidata знает
   «настольный теннис», но не «пинг-понг»; знает «Dungeons & Dragons», но не «днд». Затравка —
   ручной список ~90 тем, дальше словарь растёт от людей.

## Ключевое решение: асимметрия ввода

| Кто размечает | Как | Почему так |
|---|---|---|
| **Клуб** | сначала чипы полки → поиск по словарю → свободный ввод последним шагом | По темам клуба **ищут другие люди**. Цена разнобоя («настолки» / «настольные игры» / «боардгеймы» тремя строками) — потерянный клуб в выдаче |
| **Профиль** | свободный ввод с автодополнением, как сейчас | Самовыражение, цена ошибки ниже. Поведение не меняется — `InterestsInput` остаётся как есть |

Нормализация в проекте чисто техническая (`InterestNormalizer`: NFC → кавычки → пробелы →
lowercase → `ё→е` → 40 символов). Синонимы она **не склеивает** и не будет — вместо этого
чипы уводят от их появления.

## Два счётчика, а не один

`interests.usage_count` считает **пользователей** (`COMMENT ON` из V44 это фиксирует, на нём
сортируется автодополнение профиля). Если по нему же начать сортировать подсказки для клубов,
популярное в профилях полезет наверх в разметке клубов — а это разные вещи: «нетворкинг» частый
интерес, но редкая тема клуба.

Поэтому вводится отдельная `interests.club_usage_count`. Чипы полки сортируются по нему,
автодополнение профиля — по-прежнему по `usage_count`.

## Схема БД (V76)

```sql
ALTER TABLE interests ADD COLUMN category         club_category;  -- NULL = тема ещё не разложена
ALTER TABLE interests ADD COLUMN club_usage_count INTEGER NOT NULL DEFAULT 0;

CREATE TABLE club_interests (
    club_id     UUID NOT NULL REFERENCES clubs (id)     ON DELETE CASCADE,
    interest_id UUID NOT NULL REFERENCES interests (id) ON DELETE RESTRICT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (club_id, interest_id)
);

CREATE INDEX idx_interests_category_club_usage ON interests (category, club_usage_count DESC);
CREATE INDEX idx_club_interests_interest       ON club_interests (interest_id);
```

Основа взята из отброшенной `V60__onboarding_taxonomy.sql` (ветка `feature/onboarding`, коммит
`947b3be`) — она умерла вместе с онбордингом-с-вопросами, но модель и затравка живы. Отличия
от неё:

- `user_categories` **не переносится** — это часть онбординга/подбора, то есть срез 2;
- `users.onboarded_at` уже существует (V60 в текущей нумерации);
- добавлен `club_usage_count` (см. выше);
- `club_interests.interest_id` — `ON DELETE RESTRICT`, а не `CASCADE`. В исходнике вычистка
  строки словаря молча оторвала бы клубу тему; теперь БД такое не даст.

Затравка — ~90 тем, разложенных по 8 полкам, `ON CONFLICT (name) DO UPDATE ... WHERE category
IS NULL`: тема, уже накопленная людьми в профилях, получает полку, но `usage_count` и связи
с пользователями сохраняются. Счётчики затравка не поднимает — иначе сортировка «по
популярности» соврёт с первого дня.

## API

### Словарь

```
GET /api/interests?category=sport&limit=24   → ["бег", "йога", "футбол", ...]
GET /api/interests/suggest?q=нас&limit=10    → ["настолки", ...]        (существует, не меняется)
```

Первый отдаёт топ тем полки по `club_usage_count` — из него собираются чипы. `category`
обязателен и валидируется по `club_category`; `limit` зажимается в 1..30.

### Клуб

| Метод | Поле | Семантика |
|---|---|---|
| `POST /api/clubs` | `interests: string[]?` | отсутствует / `[]` → клуб без тем |
| `PUT /api/clubs/{id}` | `interests: string[]?` | `null` = не трогать, `[]` = очистить все, список = заменить набор целиком |
| `GET /api/clubs/{id}` | `interests: string[]` | всегда, публично |
| `GET /api/clubs` | `interests: string[]` у каждого элемента | одним батч-запросом, без N+1 |

Конвенция `null` = «не трогать» совпадает с остальными полями `UpdateClubRequest`.

**Имя поля — `interests`, не `tags`.** `ClubListItemDto.tags` уже занято вычисляемыми бейджами
каталога («Новый», «Популярный», «Свободные места») — они считаются на лету в `findAll` и к
словарю отношения не имеют.

### Авторизация

Разметка тем — часть настроек клуба, гейт `ClubCapability.EDIT_CLUB_SETTINGS` (владелец или
активный со-организатор), тот же, что у остальных полей `PUT /api/clubs/{id}`. Отдельного
права не заводится: тема клуба не про деньги и не про доступ.

### Лимиты и валидация

| Что | Значение | Где проверяется |
|---|---|---|
| Тем на клуб | максимум **7** | `InterestService.replaceClubInterests` |
| Длина темы | 40 символов | `InterestNormalizer.MAX_LEN` (общий с профилем) |
| Тем в профиле | 15 | `InterestNormalizer.MAX_COUNT`, не меняется |

Лишние темы сверх лимита отбрасываются молча (как в профиле), пустые и дубли схлопываются
нормализацией.

## Поиск каталога

`ClubFilterParams.search` расширяется с `name`/`description` на темы:

```
name LIKE %q% OR description LIKE %q% OR EXISTS (
    club_interests × interests  где  interests.name LIKE %q%
)
```

Подзапрос, а не `JOIN`: `JOIN` размножил бы строки клуба по числу совпавших тем и сломал
пагинацию с `total`.

## UX

### Создание клуба — шаг «Категория» (`CreateClubModal`, шаг 2 из 4)

Шаг уже существует (полка + тип доступа + вопрос к заявке). Под выбором полки появляется блок тем:

1. выбрал полку → раскрылись чипы её тем (топ по `club_usage_count`);
2. отмечает нужные тапом, отмеченные уезжают наверх;
3. поле поиска — если своей темы в чипах не видно, ищет по всему словарю;
4. если и поиск пуст — «Добавить своё» создаёт новую тему.

Смена полки **не сбрасывает** уже выбранные темы: человек мог отметить «бег», потом
передумать про полку — терять его выбор молча нельзя.

Счётчик `выбрано/7`, при 7 чипы гасятся. Пропустить шаг можно — темы не обязательны.

### Управление клубом (`OrganizerClubManage` → Настройки)

Тот же блок тем. Категория рядом остаётся нередактируемой — так и подписана.

### Карточка каталога (`ClubCard`)

Темы мелкими чипами отдельной строкой, максимум 3 + «+N». Не путать с бейджами
«Новый»/«Популярный» — те остаются на своём месте и в своём стиле.

### Страница клуба

Темы в блоке «О клубе», под описанием.

## Критерии приёмки

- **AC-1.** Клуб создаётся с 0..7 темами; при 8+ лишние отбрасываются, а не роняют запрос 400.
- **AC-2.** Темы клуба редактируются менеджером клуба; со-организатор может, посторонний — 403.
- **AC-3.** Категория клуба по-прежнему не редактируется — путей изменения не появилось.
- **AC-4.** Клуб с темой «настолки» находится в каталоге по запросу «настолки», даже если слова
  нет ни в названии, ни в описании.
- **AC-5.** Поиск по-прежнему находит клуб по названию и описанию — старое поведение цело.
- **AC-6.** Чипы полки «Спорт» показывают спортивные темы, «Кино» — киношные; список приходит
  из БД, а не из хардкода на фронте.
- **AC-7.** Смена полки на шаге создания не стирает уже выбранные темы.
- **AC-8.** Список каталога на 20 клубов делает **один** запрос за темами, не 20.
- **AC-9.** `usage_count` профильных интересов не меняется от разметки клубов, и наоборот.
- **AC-10.** Тема, уже существующая в словаре от профилей, при затравке получает полку и не
  теряет связи с пользователями.
- **AC-11.** Клуб без тем отображается везде корректно — пустая строка чипов не ломает вёрстку
  карточки и страницы.

## Что НЕ входит в срез 1

Рекомендации, подбор, полки «по твоим интересам», сбор интересов в онбординге, фильтр по темам
внутри полки — это срез 2, см. бэклог. Здесь только разметка, показ и поиск.
