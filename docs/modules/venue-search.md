# Поиск места встречи по заведениям (venue-search)

> Статус: **в разработке**, ветка `feature/venue-search`.
> Продолжение `docs/modules/event-geo.md` — там зафиксирован хвост «поиск по организациям —
> следующая версия». Мокап (одобрен PO 2026-08-10, вариант **A**):
> `docs/design/venue-search/mockups/01-picker.html` (папка `mockups/` в `.gitignore`).

## Зачем

Сейчас место события ищется **только по адресам**: геокодер Яндекса организации не знает
принципиально. Организатор, который проводит встречу в баре «Old Friends», вынужден искать
улицу и дом, а название заведения — вписывать руками в «Уточнение к месту». Из-за этого же
в июле место сделали опциональным (V58).

Фича возвращает нормальный сценарий: пишешь «Иваново, Old Friends» → получаешь список
подсказок с заведениями и адресами → выбираешь нужное.

## Решения PO (2026-08-10)

1. **Поиск по кнопке-лупе, а не по каждой букве.** Живого автодополнения нет: 1 поиск =
   1 запрос. Это и бережёт квоту, и совпадает с привычкой пользователя «дописал — нажал».
2. **Список подсказок**, из которого пользователь выбирает строку. Заведения и адреса —
   **вперемешку в одном списке**, без вкладок и переключателей.
3. **Пусто — значит пусто**: подсказок нет → списка нет, показываем одну строку.
4. **Вариант C макета** (пересмотр 2026-08-10 в пользу C вместо A): список всплывает
   **шторкой поверх карты** и закрывается после выбора. Причина отказа от A: там на время
   показа списка карта скрыта, а человек, который не знает названия заведения и
   ориентируется по карте, должен видеть, где находятся предложенные варианты. Высота шита
   при этом не меняется — в проекте уже был баг с прыгающей высотой модалки под клавиатурой.
5. Провайдер — **API Геосаджеста Яндекса, бесплатный тариф**. Разбор альтернатив и почему
   отвергнуты ППО / 2ГИС / OSM — в § «Почему именно Геосаджест».

## Провайдер и лимиты

| | |
|---|---|
| Продукт | «API Геосаджеста», отдельный от JS API / Геокодера / Static API |
| Тариф | Бесплатный, **1 000 запросов в сутки** (`yandex.ru/legal/maps_api/ru/`, п. 6.4) |
| Эндпоинт | `GET https://suggest-maps.yandex.ru/v1/suggest` |
| Ключ | env бэкенда `YANDEX_SUGGEST_API_KEY`, **на клиент не уезжает** |

⚠️ **Геосаджест НЕ возвращает координаты** — только `title`, `subtitle`, `address`, `tags`
и `uri`. Поэтому выбор места стоит **двух** запросов:

```
лупа   → 1 запрос: Геосаджест (attrs=uri)        → список подсказок
выбор  → 1 запрос: Геокодер по uri выбранной     → координаты точки
```

Оба сервиса бесплатные и оба уже проксируются бэкендом. Ключ геокодера переиспользуется —
новых продуктов подключать не нужно.

### Почему именно Геосаджест

- **ППО («API Поиска по организациям»)** — эталон качества, но бесплатного HTTP-режима нет:
  от 195 000 ₽/год. Обещанная «тысяча запросов ППО внутри бесплатного JS API» действует
  только для ключей, активных на 20.04.2025; наши созданы позже. Проверено экспериментом:
  на нашем ключе `ymaps.suggest()` → «Suggest is not available»,
  `SearchControl{provider:'yandex#search'}` → `scriptError`.
- **2ГИС** — оферта (п. 3.1) запрещает сохранять полученные данные, «кэширование не
  предусмотрено». Модель «выбрал кафе → сохранили в `events`» нарушает договор напрямую.
- **OSM (Photon/Nominatim/свой дамп)** — проверено живыми запросами: в Иваново с рамкой
  города «Old Friends» → пусто, «кофейня» → выдача из Ростова Великого, Владимира, Мурома.
  Данных по России нет, пайплайн их не родит. Публичный Nominatim вдобавок прямо запрещает
  автокомплит.

## Контракт API

### `GET /api/geo/suggest`

Подсказки по строке. Под JWT и общим `RateLimitFilter`, как весь `/api`.

| Параметр | Тип | Обяз. | Смысл |
|---|---|---|---|
| `q` | string, 3..200 | да | Строка запроса как её ввёл пользователь |
| `clubId` | UUID | нет | Клуб встречи — по нему поиск сужается до города клуба |

```jsonc
200 OK
{
  "results": [
    {
      "title":    "Old Friends",
      "subtitle": "Кальян-бар · Иваново, Пограничный переулок, 62",
      "address":  "Иваново, Пограничный переулок, 62",
      "kind":     "business",          // business | house | street | other
      "uri":      "ymapsbm1://org?oid=1024394521"
    }
  ]
}
```

- Подсказок нет → `200` с пустым `results` (**не** 204: пустой список — валидный ответ
  для списочного эндпоинта, в отличие от `/geocode`, где 204 значит «адрес не найден»).
- Геосаджест недоступен / ключ не настроен → `503`, как у геокодера.
- Подсказки **без `uri` отбрасываются** на бэкенде: без него координату не достать,
  а мёртвая строка в списке хуже её отсутствия.

### `GET /api/geo/resolve`

Координаты выбранной подсказки.

| Параметр | Тип | Обяз. | Смысл |
|---|---|---|---|
| `uri` | string | да | `uri` из подсказки, как есть |

```jsonc
200 OK   { "address": "…", "lat": 57.01283, "lon": 40.972935 }
204      // uri не разрешился
503      // геокодер недоступен
```

Отдельный эндпоинт, а не параметр у `/geocode`: там `q` — строка запроса, здесь `uri` —
непрозрачный идентификатор Яндекса, и смешивать их в одной валидации значит плодить
взаимоисключающие ветки.

### Лимиты и валидация

- `/api/geo/*` живёт в **отдельном bucket'е `RateLimitFilter` — 12 запросов в минуту**
  (общий лимит 60/мин не годится: каждый запрос тратит суточную квоту, общую на всё
  приложение, а один `/suggest` стоит до двух обращений в Яндекс).
- `uri` проверяется по формату `^ymapsbm1://…` **до** похода в сеть — иначе `/resolve`
  был бы доступом к нашему платному ключу геокодера произвольной строкой.
- Нечитаемый `clubId` → `400`, а не `500` (обработчик `MethodArgumentTypeMismatchException`).
- Отложено и записано в `docs/backlog/venue-search-quota-hardening.md`: суточный
  предохранитель в Redis, кэш подсказок, IP-ключевание лимитов, общий транспорт к Яндексу.

### Сужение до города клуба

Координаты города бэкенд достаёт **сам**: `clubId` → `clubs.city_id` → `cities.latitude/longitude`
(V74, поля `NOT NULL`). Клиенту координаты не отдаются, лишнего поля в DTO клуба не заводим.

- Есть город → `ll=<lon>,<lat>`, `spn=0.6,0.6` (≈60 км, чтобы попадал пригород),
  `strict_bounds=1`.
- **`strict_bounds` обязателен.** Без него `ll`+`spn` — лишь мягкое смещение: запрос
  «антикафе» рядом с Иваново вытащил Астану, Москву и Волгоград. Со строгой рамкой —
  только Иваново.
- **Фолбэк:** если со строгой рамкой пришло 0 подсказок — один повторный запрос **без**
  рамки. Иначе загородная база отдыха или клуб без города превращаются в «ничего не нашли».
  Стоит это до 2 запросов и только в пустом случае.
- Клуба нет / город не указан → ищем без рамки сразу.

## Поведение пикера (вариант C)

Карта видна **всегда**. Список подсказок — отдельный слой поверх неё.

| Состояние | Что на экране |
|---|---|
| `map` (стартовое) | строка поиска + карта с пином по центру |
| `results` | то же + **шторка со списком поверх карты**, карта видна снизу |
| `empty` | то же + строка «ничего не нашли», шторки нет |

- Лупа → запрос → есть подсказки → шторка; пусто → строка «ничего не нашли».
- Тап по строке → `/resolve` → шторка закрывается, карта летит к точке
  (`PICKER_ZOOM_FOCUSED`), над картой «✓ <название> — уточните точку, потянув карту».
- **Тап мимо шторки закрывает её** и возвращает карте жесты — пользователь может
  осмотреться и открыть список снова той же лупой (без нового запроса, результат
  держим в состоянии).
- Шторка занимает не всю высоту карты (≈2/3), чтобы карта под ней читалась. Список
  внутри скроллится, страница и карта при этом не двигаются (`overscroll-behavior: contain`).
- Высота шита не меняется ни в одном состоянии — шторка позиционируется абсолютно.

**Почему не A и не B.** A прячет карту, пока открыт список, — не годится тому, кто
ориентируется по карте, а не по названию (замечание PO). B показывает оба блока сразу, но
на телефоне зажимает и список, и карту до нечитаемых размеров.

### Ловушка «Готово» затирает название

Сейчас `handleDone` **всегда** делает обратный геокодинг по центру карты. Если оставить как
есть, выбранное «Old Friends» превратится в «Пограничный переулок, 62» — то есть фича
сломает сама себя.

Правило: после выбора подсказки запоминаем точку и текст. На «Готово»
- центр карты **не сдвинут** относительно выбранной точки (дельта < ~1e-6) → отдаём
  сохранённый текст, обратный геокодинг **не вызываем** (заодно экономим запрос);
- центр сдвинут → пользователь уточнил место руками, поведение прежнее: обратный
  геокодинг, название заведения теряется осознанно.

### Что уходит в `location_text`

Собирается **из ответа саджеста**, а не из геокодера: геокодер по `uri` организации
возвращает адресом её название («Россия, …, Иваново, Old Friends»), что бесполезно.

- Заведение (`kind=business`): `«<title>, <address>»` → `Old Friends, Иваново, Пограничный переулок, 62`
- Адрес (`house`/`street`): `<address>` как есть
- Ручной пин: как сейчас — текст обратного геокодинга

⚠️ **Подзаголовок подсказки не склеивать вслепую.** При `print_address=1` Яндекс уже кладёт
в `subtitle.text` связку «рубрика · адрес», и вторая склейка давала дубль адреса. Документацией
это не закреплено, поэтому адрес приклеивается, только если его ещё нет в рубрике — код
корректен при обоих вариантах ответа. Поймано живым запросом, на синтетической фикстуре
(где `subtitle` был просто «Кальян-бар») баг не воспроизводился.

### Ещё одна ловушка: анимация перелёта

`panTo` летел к выбранной точке 300 мс, а `handleDone` читает `getCenter()` синхронно.
Успевший нажать «Готово» получал промежуточную координату анимации — то есть точку, которую
никто не выбирал. Поэтому перелёт к подсказке **мгновенный** (`duration: 0`), а «Готово»
заблокирована, пока едут координаты выбранной строки (иначе у не двигавшего карту в событие
уезжала бы Москва из `DEFAULT_CENTER`).

Схема БД **не меняется**: `location_text` (V5/V58), `location_lat/lon`, `location_hint`
(V57) уже есть, новых колонок и миграций не нужно.

## Критерии приёмки

1. `Иваново, Old Friends` + лупа → в списке первой строкой заведение «Old Friends,
   Кальян-бар, Пограничный переулок, 62».
2. `Иваново, Ленина` → в одном списке и улица/дома, и заведения на них.
3. `Иваново, Блаблабла Пыщь` → списка нет, показана строка «ничего не нашли», карта на месте.
4. Тап по подсказке → шторка закрылась, карта переехала на точку, над картой название
   выбранного места.
4a. Карта видна из-под шторки, пока список открыт; тап мимо шторки её закрывает и
   возвращает карте жесты, повторная лупа открывает тот же список без нового запроса.
5. «Готово» сразу после выбора → в форме события **название заведения**, не улица.
6. Сдвинул пин после выбора → в форме адрес из обратного геокодинга (прежнее поведение).
7. Поиск сужен городом клуба: одинаковый запрос в клубах разных городов даёт разные выдачи.
8. Ключ Геосаджеста не настроен → `503`, пикер показывает «поиск временно недоступен»,
   поставить точку пином по-прежнему можно (fail-open, как у геокодера).
9. Ключ Геосаджеста отсутствует в бандле фронтенда (`grep` по `dist/`).

## Юридический хвост

П. 5.1.5 условий Яндекса запрещает хранить ответы сервисов дольше 30 дней, а место встречи
лежит в `events` бессрочно. **Это положение не новое** — `location_text` и сейчас является
ответом геокодера (с 2026-07-11). Фича его не ухудшает. Снижение риска: храним только
подтверждённые пользователем название и адрес плюс координату, и **не** сохраняем рубрики,
телефоны, часы работы, `uri` и прочие поля ответа.
